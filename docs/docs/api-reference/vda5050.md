# VDA 5050 v3.0.0

amr-fleet-control is **Conformist** to VDA 5050 v3.0.0 (relationship 6, decision D2,
[ADR 0002](/docs/adr/0002-vda5050-v3-conformance-map-and-traffic-control)). Its wire types,
`internal/adapters/vda5050/messages.go`, are copied byte for byte from the robot side it conforms to, the equipment
emulator; the robot-side subset is the emulator's
[`docs/vda5050-subset.md`](https://github.com/IQVO/equipment-emulator/blob/v0.1.0/docs/vda5050-subset.md) at `v0.1.0`.
No v2 support: a v2 robot would need a second codec and topic prefix behind the same `ports.Downlink`.

## Transport

| Rule | Value |
| --- | --- |
| Protocol | MQTT 3.1.1, QoS 1, JSON |
| Topics | `vda5050/v3/<manufacturer>/<serialNumber>/<topic>` |
| Published by fleet control | `order`, `instantActions` (never retained) |
| Subscribed (wildcards, in this order) | `connection` (retained), `factsheet` (retained), `state` |
| Clients | ONE MQTT client for the whole fleet (`MQTT_CLIENT_ID`), one inbox, one worker: every robot message and every 1 s tick in arrival order |

## Header

Every message carries `headerId` (counting per topic and robot, taken in the ordered sender, so `headerId` order is
wire order), `timestamp` (`2006-01-02T15:04:05.000Z`, fleet control's own clock), `version` `3.0.0`, `manufacturer`
and `serialNumber`. An inbound message whose topic and header name different robots, or whose `version` is not
`3.0.0`, is dropped as invalid; a zero-length payload (a cleared retained message) is ignored.

## Orders

| Rule | As built |
| --- | --- |
| Order id | The leg id (`leg-<uuid>`) for a leg; `ms-<uuid>` for an internal CHARGE or PARK mission. One leg = one mission = one order (D4). |
| Sequence ids | Node `i` of the route has `sequenceId` `2i`; the edge into it `2i-1` (D8). |
| Nodes | Every node carries `nodePosition` (`x`, `y`, `mapId`). |
| Base and horizon | Released (base) up to at most `RELEASE_AHEAD_NODES` past the robot's last reached node, and only after every node and edge of the new stretch was reserved for that robot; the rest of the route is horizon. |
| Updates | `orderUpdateId` starts at 0 and rises by exactly 1 per base extension and per re-route; an update starts at the previous base end with its sequence id. |
| Edge actions | Never sent. |
| Node actions | `pick` (parameter `loadId` = container id, action id `<leg>-pick`), `drop` (`<leg>-drop`), `startCharging` (`<mission>-startCharging`), all `HARD` blocking. |
| Acceptance | An order counts as accepted when a `state` shows its `orderId` and `orderUpdateId`. |
| Resend | An unacknowledged order is resent with the SAME `orderUpdateId` after `ORDER_RESEND_AFTER_SECONDS`; the robot answers an equal one with `SAME_ORDER_UPDATE_ID`, which is harmless. |

## Instant actions

| Action | Sent when | Action id |
| --- | --- | --- |
| `cancelOrder` (`HARD`) | a leg is cancelled while ASSIGNED, a leg fails after its order went out, a robot reports a pending order fleet control does not own | `<leg>-cancel`, `recover-<uuid>` for an unowned order |
| `stopCharging` (`HARD`) | a charging robot without a mission reaches `CHARGE_RESUME_PERCENT` (resent after `ORDER_RESEND_AFTER_SECONDS` while unanswered) | `stop-<uuid>` |
| `stateRequest` (`NONE`) | to every known robot in `Recover`, at boot | `state-<uuid>` |

`factsheetRequest` is declared in `internal/application/vda` but never sent: the factsheet is retained and arrives with
the subscription. A robot with a `cancelOrder` in flight is never offered an order until the robot answers it
(`FINISHED` or `FAILED`) or the cancel is given up after `ORDER_RESEND_LIMIT` re-sends.

## The rejection rule (D19)

There is no reply topic: a rejection arrives only as a `WARNING` error in the robot's next `state`. The emulator
appends one `VALIDATION_FAILURE` or `INVALID_ORDER` entry per rejection and clears its error list on acceptance, so
fleet control counts an order as rejected when the number of those entries RISES between two reports while the
order is unacknowledged, or after `ORDER_RESEND_LIMIT` resends without acknowledgement. Either fails the leg
`ORDER_REJECTED` with `robot_error` = the newest rejection type. The emulator keeps only its newest 50 errors, so a
rejection on a full list is caught by the resend limit instead.

## State reports

A `state` is a full snapshot applied in arrival order (no inbox table). It gives the robot's connection-independent
facts: `lastNodeId` and `lastNodeSequenceId` (progress), position, battery and charging, errors (a `CRITICAL` or
`FATAL` one makes the robot `HELD`), loads, and the `actionStates` and `instantActionStates` that drive pick, drop,
charge and cancel. Its header `timestamp` becomes `robot_timestamp` on the facts it produces.
